## 2. RAG 답변 신뢰도 (실질적 — 정상 사용에서 상시 발생)

이 앱의 핵심 산출물은 신학 답변이므로 우선순위가 가장 높다. 모두 보안이 아닌 **충실도(faithfulness)** 결함.

- **[medium] 관련성 임계값 부재 → 무관 청크 강제 인용** (`retrieve.py:18-32`, `web.py:260-338`)
  `search()`는 거리(distance)를 계산만 하고 임계값 필터가 없어, 질문이 코퍼스와 무관해도 항상 top_k를 반환한다. 시스템 지시는 "각 주장 뒤 [저작명, p.페이지] 표기"를 강제하므로 무관 발췌가 권위 인용처럼 붙는다. 사용자는 진짜 근거로 오인.
  → 수정: `search()`에 `max_distance` 추가, 초과 시 드롭. hits 비면 "근거 부족·추측 금지" 분기. bge-m3 컷오프 0.6~0.7 캘리브레이션.

- **[low] symposium 경로의 검색 실패 무음화 → 0-근거 상태로 페르소나 답변** (`web.py:604-616, 662-668`)
  `/api/ask`는 hits 없으면 404로 막지만, symposium 경로는 `except: hits=[]`로 삼킨다. 페르소나 유지 + 인용 강제 + 면책 금지가 결합돼 저작명·페이지를 지어낸다. 현재 57저자 전원 컬렉션 보유라 정상 UI로는 미발화이나, 한 코퍼스만 누락돼도 그 신학자만 조용히 환각.

- **[low] 용어집 부분문자열 매칭 오탐** (`web.py:216`)
  단어경계 무시로 `law`→`lawn`, `sin`→`single`, `age`→`management`, `죄`→`죄송`이 매칭돼 무관한 번역을 "반드시 따르라"고 강제. 3~4자 표제 89개가 고위험.
  → 수정: 영어는 `\b…\b` 정규식, 한국어는 최소길이 상향/형태소.

- **[low] 용어집이 청크 앞 200자만 스캔** (`web.py:262, 308`)
  프롬프트엔 800자 전체가 들어가는데 용어 추출은 `[:200]`만 봐서 뒤 75% 용어는 번역 강제 누락. → 슬라이스를 CHUNK_SIZE와 일치.

- **[low] 히스토리 라벨 위조 주입** (`web.py:329-335`)
  히스토리를 `[이름] {text}` 평문 이어붙임. message(4000자)에 개행+`[칼뱅] …` 위조 라벨 삽입 시 다른 신학자 발화처럼 오염. RCE는 `--tools ""`로 차단, 피해는 자기 세션 답변 품질에 한정.

## 3. 구독 쿼터·자원 낭비

- **[low] 클라이언트 disconnect 시 claude subprocess 고아 실행** (`web.py:353-392`) — 확증
  `proc.kill()`이 `except TimeoutError` 분기에만 있고, 취소는 `finally`에서 회수 안 됨(로컬 `sleep 5` 재현). 5명 향연 중 이탈 시 진행 중 호출(최대 90초)이 쿼터 계속 소모. 락·카운터는 정상 해제.
  → `finally`에서 `if proc.returncode is None: proc.kill(); await proc.wait()`, 취소는 재-raise.

- **[low] SSE 루프에 disconnect 검사 없음** (`web.py:601-640`)
  이탈해도 남은 신학자 전원 호출 지속 + 락 점유로 큐 적체. (제안된 `request.is_disconnected()`는 핸들러 시그니처에 `request` 없어 그대로는 미동작 — 시그니처 추가 필요.)

- **[low] chroma 클라이언트 호출당 재생성** (`retrieve.py:20`) — 확증
  `@lru_cache`는 임베딩 모델에만. `PersistentClient`는 매 `search()` 신규. 한 라운드에 N+1회 재오픈 → 첫 응답 지연.
  → 모듈레벨 `@lru_cache`로 `_get_client(chroma_dir)`·`_get_collection(chroma_dir, author)` 분리(재인덱싱 시 서버 재시작 명시).

- **[low] 본문 크기 상한 chunked 우회** (`web.py:92-102`) — 확증(경험적)
  `Content-Length`만 검사 → `Transfer-Encoding: chunked`면 검사 스킵, 본문 전량 메모리 버퍼. 실측: CL 300KB→**413**, chunked 300KB→**422**(본문 다 읽고 Pydantic 거부). 필드 max_length가 2차 방어이나 메모리 증폭 방어는 뚫림. 전제=로컬/인증 공격자.

## 4. 인증/세션 위생 (미래 견고성)

- **[low] 게이트가 화이트리스트(host 1개) 의존** (`web.py:48,76-89`)
  현재 안전하나, 2차 터널규칙·추가도메인·리버스프록시·0.0.0.0 재노출 중 하나만 생겨도 새 Host/IP는 무게이트 전면개방. → **deny-by-default 반전**: "루프백만 무게이트, 그 외 전부 게이트". 미래 노출에 자동 견고.

- **[low] JWT aud/iss/typ 미검증** (`web.py:57-73`)
  서명·exp·role만 검증. Alexandria와 시크릿 공유라, 향후 approved인데 Symposium은 불허할 별도 토큰 부류가 생기면 경계 붕괴. 위조는 불가(HMAC 온전). → 발급측에 `aud="symposium"` 추가 후 강제 검증.

- **[low] 세션에 소유자(JWT 신원) 미결합** (`session.py:44-65`)
  session_id만 알면 다른 인증 사용자도 이어붙임. 144비트라 열거 불가, 유출(로그/공유링크) 전제. → 외부 게이트 환경에서 세션에 JWT sub 기록·대조, 로그 마스킹.

- **[low] 게이트·JWT 검증 회귀 테스트 전무** (`tests/`)
  외부 노출 유일 방어선인데 무테스트. 리팩터로 의미론 뒤집혀도 회귀 미포착. → 게이트 6종 케이스 + `_verify_alex_jwt` 단위 테스트.

## 6. 심층방어 관찰 (현재 양성, 멘탈모델 정정)

- **[info] `--tools ""`가 advisor/MCP까지 봉인하진 않음** (`web.py:367`)
  재현: `--tools ""` 하에서도 advisor 도구 생존(2+2 호출 성공). `--strict-mcp-config` 부재라 전역 `~/.claude.json`의 MCP 상속 → 실제 잔여 능력이 코드가 아닌 전역 config에 좌우. 향후 셸형 MCP 추가 시 자동 상속. advisor는 호스트 실행 아니라 즉각 RCE는 아님. → argv에 `--strict-mcp-config` 추가로 코드 레벨 봉인.
- **[info] SessionStart 훅은 tools 게이트 밖에서 매 호출 실행** — 전역 `cmux-session-record.sh`가 매 `_call_claude`마다 실행(프롬프트 비제어라 현재 양성). 향후 프롬프트 기반 훅(PreToolUse 등) 추가 시 입력이 훅 경유로 셸에 닿을 수 있음. → 서버 전용 `CLAUDE_CONFIG_DIR` 격리로 훅/MCP/권한 상속 차단(심층방어).

## 7. 개선 가설 (장점/단점)

- **라이트/다크 테마 토글** — 이미 `:root` 변수화 완료(오늘 0.15.1) 기반.
  - 가설: `[data-theme='light']` 오버라이드 + 헤더 토글 + localStorage + `prefers-color-scheme` 초기값.
  - 장점: 인프라 이미 있어 비용 최소, 밝은 방송실/프로젝터 가독성, CSP 충돌 없음(외부 JS 토글).
  - 단점: 라이트 팔레트 균형 재설계 필요(단순 반전 저품질), era 색(JS 하드코딩) 대비 재검토, 소수 단일취향이면 ROI 낮음.
- **요청 관측성(구조화 로그)** — `_security_middleware`에 소요/status/path, `_call_claude`에 지연/rc/waiter.
  - 장점: 비개발자 운영자 장애 진단·쿼터 추이 가시화, 미들웨어에 얹어 침습 최소.
  - 단점: 질문 본문 로깅 시 프라이버시/저작 노출(본문 제외·해시만), 로테이션 없으면 디스크 증가.
- **세션 지속화 + 자산 백업** — SQLite write-through + chroma/metadata/glossary tar 스냅샷.
  - 장점: 재시작·배포 후 진행 대화 보존, 재인덱싱 원천 손실 방지, SQLite 단순.
  - 단점: 동시성/TTL/LRU를 DB로 옮겨 복잡도↑(현재 단순함이 장점), 저작권 사본 증가로 보관통제 필요. 우선순위 백업 > 세션지속화.
- **답변 토큰 스트리밍** — SSE 인프라 재활용, `--print`→스트림 출력.
  - 장점: TTFT 대폭 개선(최대 불만인 90초 대기 해소), disconnect 조기중단과 시너지.
  - 단점: stream-json 파싱·부분토큰 조립 복잡, direct 엔드포인트 SSE 전환+프런트 재작성, CLI 버전 의존↑.
